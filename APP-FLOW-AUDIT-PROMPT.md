# Full-App Flow Audit — reusable prompt

Copy-paste this into a fresh Claude conversation for any multi-role app (marketplace,
SaaS, booking platform, whatever has more than one type of user). Fill in the
bracketed parts. This is the same structure that found the double-booking hole,
the price-tampering bug, and the "reviews can never be written" chain in SoulsWed.

---

## The prompt

```
[APP URL] is my app. Do a full flow audit across every role, not just a code
read — actually exercise the flows and tell me where they break.

Roles and test credentials:
- [Role 1, e.g. Customer]: [email] / [password]
- [Role 2, e.g. Vendor/Provider]: [email] / [password]
- [Role 3, e.g. Admin]: [email] / [password]

For each role, walk the primary journey end to end (signup → core action →
outcome) and check:

1. STATE HANDOFFS BETWEEN ROLES
   Does an action by Role A actually become visible to Role B in the way the
   product promises? E.g. does a customer's booking/order/request show up
   correctly on the provider's side, with the right identity, the right
   status, and nothing missing or duplicated? This is the category most bugs
   hide in — two roles each with their own view of the same underlying record,
   built at different times, quietly disagreeing.

2. MONEY / VALUE INTEGRITY (if the app handles payments or pricing)
   - Is any price, discount, quantity, or total ever taken from the client
     request instead of recomputed server-side from the database? (Try editing
     a request in devtools — can you pay ₹1 for something that costs ₹1,000?)
   - Do the payment-confirmation redirect and the payment-provider webhook
     both exist, and does the webhook (not just the redirect) authoritatively
     mark the transaction complete? A closed tab should never leave a paid
     order stuck "unpaid."
   - Do two different screens that both compute revenue/earnings/payouts
     agree with each other? (Check admin totals vs. the provider's own view.)

3. LIFECYCLE / STATUS MACHINE
   - List every status a core record (order/booking/ticket/application) can
     have. For each transition, who is allowed to trigger it, and is that
     enforced server-side or only hidden in the UI?
   - Is there any status that's supposed to be reachable but nothing in the
     code actually triggers the transition? (This is how "completed" and
     "reviews" both silently broke in one app — nothing ever flipped the
     status, so the thing gated behind it was unreachable too.)
   - Are "business state" (pending/confirmed/cancelled) and "payment state"
     (unpaid/paid/refunded) modeled as separate fields, or conflated into one?
     Conflating them usually hides a bug (e.g. "confirmed" bookings that were
     never actually paid for).

4. IDENTITY / ID CONSISTENCY
   - If the same real-world thing (a listing, a product, a user) can be
     referenced by more than one ID format anywhere in the codebase (a slug
     vs. a raw database ID, for instance), check whether every query that
     matches on that ID handles both forms. A mismatch here causes silent
     data loss (records invisible to the owner) or worse, double-booking /
     double-allocation, since a conflict check that only matches one ID format
     doesn't see records stored under the other.

5. AUTH AND SESSION SECURITY
   - Can a request forge or bypass 2FA/OTP by sending its own identity in the
     request body instead of the server reading it from an authenticated
     session? (Test: does the OTP-verify endpoint trust a posted email/role,
     or does it look up who actually passed the password step?)
   - Is there rate limiting on login, OTP guesses, password reset, and any
     public form that triggers outbound email? Check the actual number
     (a 6-digit OTP with unlimited guesses is crackable in minutes).
   - Does route-level access control check role, not just "is logged in"?
     Try hitting another role's dashboard URL directly while logged in as a
     different role.
   - Are passwords/tokens ever compared with plain `===` instead of a
     constant-time comparison? (Timing attacks are usually low-priority, but
     worth flagging.)

6. CROSS-ROLE ADMIN VISIBILITY
   - Can admin see every real transaction/review/record generated by actual
     usage, or does an aggregation query only look at one data source when
     the app actually has two or three? (This is how admin review moderation
     showed zero reviews while real reviews existed elsewhere in the DB.)
   - Do admin-facing counts (e.g. "total customers," "total revenue") use the
     same filter logic everywhere they're computed, or does each screen have
     its own hand-rolled version that can drift out of sync?

7. PRODUCTION / DEPLOYMENT ENVIRONMENT
   - If this deploys to a serverless platform (Vercel, Lambda, Cloud Run):
     does anything hold state in process memory (rate limits, caches,
     in-flight locks) that would silently stop working because instances
     don't share memory? Anything stateful needs to live in a shared store
     (DB, Redis), not a variable.
   - Is any secret (DB password, session secret, API key, webhook secret)
     committed to git history, even if `.env` is gitignored now? (`.gitignore`
     doesn't retroactively untrack already-committed files — check
     `git log --all --full-history -- .env`.)
   - Are environment variables actually set in the hosting platform's
     dashboard, not just locally? Do redirect URLs / webhook URLs point at
     the production domain, not localhost?

8. EDGE CASES WORTH TRYING BY HAND
   - Submit a form with a required field missing, a negative number, an
     absurdly large number, and a value in the wrong type.
   - Do the exact same action twice in a row fast (double-click submit) —
     does it create two records?
   - Log in as Role A, then open a URL that belongs to Role B's dashboard.
   - Cancel/refresh mid-flow (e.g. close the tab right after payment starts,
     before redirect) and check the record's state afterward.

Give me the findings as a severity-ranked list (P0 = exploitable/data-loss,
P1 = broken core flow, P2 = inconsistent/confusing, P3 = cosmetic), with the
exact file and line where each bug lives, and what a correct fix looks like —
not just "this is broken."
```

## Notes on using this

- Give it real (test/dummy) credentials for each role — an audit that can't
  actually log in and click through will only ever be a code read, and misses
  the bugs that only show up when two roles' views of the same data actually
  disagree.
- Ask for fixes in batches, confirm one batch is deployed/working before
  starting the next, rather than approving everything at once — easier to
  isolate what broke if something regresses.
- After fixes, ask for a small regression test suite covering exactly the
  bugs found (not generic coverage) — that's what stops them from quietly
  coming back.
